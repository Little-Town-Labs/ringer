# Shared evidence store on aegis-prod

**Status**: Draft for review. No production mutation is authorized by this document.

## Approval and scope
Brownfield / system / routine. Gary wants Ringer attempt evidence from any tailnet machine (powerbox2, powerbox3, powerstation) visible and reportable in one place, because Ringside is only reachable on the machine running Ringer. This spec supersedes ADR-001's deferral of central evidence; it needs its own ADR (docs/decisions/002-shared-evidence.md) that records why ADR-001's "preserve existing PostgreSQL behavior" is changed for the new backend.

## Findings that shape this spec
- `swarm_runs` has no DDL in the repo; the shipped table was created by hand in Supabase.
- `EvalLogger.log_attempt` (ringer.py) writes 12 columns and drops `model`, `task_type`, `reasoning_effort`, `retry` (and `expected_model`, `reported_model`, `logged_at`, `log_sink`, `fallback_reason`). The model scoreboard and pass-rate slicing depend on `model` and `task_type`.
- `run_id` + `task_key` is not unique per attempt (docs/EVIDENCE.md), and the insert has no unique key, so retried or re-imported rows would duplicate.
- On any Postgres failure the logger silently falls back to local JSONL; the only trace is `fallback_reason` inside the row.
- `spec` holds full prompt text, including worktree paths.
- aegis-prod: dedicated tailnet-only listener needed; `psql`, `docker`, `python3` present, no `duckdb`; existing Postgres containers belong to other apps; Grafana already runs there. DuckDB files allow one writer, so DuckDB is a reporting client, never the shared write target.

## Requirements
- R1: Provide a dedicated `ringer` Postgres database (own container and volume, own credentials) on aegis-prod, bound to the Tailscale address only (`100.100.1.21:5440`, direct tailnet port, not proxied; Postgres is not HTTP and Tailscale already encrypts transport). It must not share a database, role, or volume with any other application. Provisioning is a separate, explicitly approved production change; this spec delivers the SQL (`schema.sql`) and a reviewed compose file only.
- R2: The central table stores every field of a `runs.jsonl` row: `model`, `task_type`, `reasoning_effort`, `retry`, `expected_model`, `reported_model`, `logged_at`, `log_sink`, `fallback_reason` included. See `schema.sql`.
- R3: Each attempt has a client-computed `attempt_uid` = sha256 of `source_host | logged_at | run_id | task_key | worker_engine`, using the exact `logged_at` string written to JSONL. `EvalLogger` stamps `logged_at` and `attempt_uid` once, before either sink, so a row has the same identity whichever sink stores it. Inserts use `ON CONFLICT DO NOTHING` with no conflict target: naming `(attempt_uid)` as the arbiter would require the insert-only writer role to hold SELECT (verified against Postgres 16), and `attempt_uid` is the table's only non-identity unique constraint.
- R4: Backward compatibility. The shipped 12-column `INSERT INTO swarm_runs` keeps working against the new database unchanged (compatibility view plus server-side defaults in `schema.sql`), so machines can be pointed at it before the code change lands.
- R5: Prompt policy for `spec`: `[eval.postgres] spec_storage = "hash" | "excerpt"`. Default is `hash`: store only `spec_sha256` and leave `spec` NULL. `excerpt` stores the `spec` text exactly as it appears in the row, which the runner has already cut to 500 characters (`ringer_core/runner.py`), so no separate "truncated" mode exists. Rows for tasks with `redact_spec` carry `[redacted request packet]` and are always hash-only. Rationale: a shared database should not receive prompts and paths by default.
- R6: Failure visibility. A failed Postgres write still falls back to JSONL (the local row records `log_sink = "jsonl"` and a Postgres-worded `fallback_reason`), and additionally emits one stderr line per run (not per row) naming the reason. `ringer evidence status` is local-only (the writer credential cannot read): it reports row counts per file, how many rows have `log_sink = "jsonl"` (never reached Postgres), and the most recent `fallback_reason`.
- R7: `ringer evidence push [--file PATH ...] [--since TS] [--source-host NAME] [--dry-run]` sends local JSONL rows to the central store, idempotently (R3). Default input is the configured `[eval] jsonl_path`; other files (for example a legacy `~/.ringer/runs.jsonl`) are passed with `--file`. Because the writer role cannot read the table, every push re-sends all selected rows and relies on `ON CONFLICT DO NOTHING`; the command reports inserted versus already-present from row counts. Each file goes in one transaction. It preserves each row's original `log_sink` and `fallback_reason`, reads JSONL only, and never modifies or truncates it. `--dry-run` parses and validates rows and reports counts without connecting. A malformed row aborts that file with its line number and sends nothing from it.
- R8: Least privilege. Two roles: `ringer_writer` (INSERT only) and `ringer_reader` (SELECT on tables and views only). Machines receive only the writer credential; reporting tools receive only the reader credential. Credentials live in env files outside the repo; none appear in code, docs, tests, or logs.
- R9: Reporting. The schema provides `model_scoreboard` and `daily_activity` views. Grafana (already on aegis-prod) and DuckDB (via its `postgres` extension, run from any machine) read the views with the reader role. No DuckDB file is written on aegis-prod.
- R10: Local JSONL stays the default backend. When `[eval] backend = "postgres"`, `EvalLogger` writes **both**: JSONL always, Postgres in addition (today it writes one or the other and returns after a successful insert, which would leave Postgres-only rows with no local copy). `log_sink` records where the database write landed: `postgres` on success, `jsonl` on fallback (with `fallback_reason`). `evidence push` therefore never needs to know which rows are already central; it relies on R3 idempotency and preserves each row's original `log_sink` and `fallback_reason`. Headless defaults from spec 001 are unchanged.
- R11: Tests use a throwaway local Postgres (container) or a fake `psycopg` connection; no test touches aegis-prod. Cover: idempotent re-push, uid stability across sinks, legacy 12-column insert against the schema, spec_storage modes, outage fallback plus later push, and writer/reader privilege separation.
- R12: Neutral naming. The database is not Supabase. Accept `RINGER_DB_HOST/PORT/USER/PASSWORD/NAME` in the env file, fall back to the legacy `SUPABASE_DB_*` keys for existing files, and rename user-facing messages and `fallback_reason` text from "Supabase" to "Postgres". The `[eval.postgres] env_file` setting is unchanged.
- R13: Backup. A host cron job on aegis-prod runs `pg_dump` nightly into `~/ringer-postgres/backups/` (owned by the service user, so no sudo), keeping 14 daily dumps. Because every machine keeps its full local JSONL (R10), the central database can also be rebuilt by re-running `evidence push` from each machine. No retention limit on rows: volume is tiny (124 attempts in about two months).

## Non-goals
- Live "who is running now" state. Attempt rows exist only after an attempt finishes; central live status (shipping `runs/*.json` snapshots, or serving Ringside from aegis-prod) is a follow-up spec.
- A DuckDB ingestion service, DuckDB as write target, or changes to the SQLite analytics flow.
- Sharing, migrating, or reading any existing aegis-prod database.
- Multi-user auth beyond the two roles, TLS beyond Tailscale transport, high availability, retention policy (backup/retention is an open question below).
- Changing manifest, worker, or verification behavior.

## Decisions on the former open questions
1. **`spec` storage**: default `hash` (R5). Local JSONL rows already carry `spec` truncated to 500 characters (observed: max 500 across 323 rows), so neither store has the full prompt; the full text lives only in the manifest and worker log. `spec_sha256` is therefore a hash of the stored (truncated) text, not of the full prompt. The central store does not copy even that excerpt by default. Per-install override via `spec_storage`.
2. **Other consumers of `swarm_runs`**: none. Supabase is not in use, so no external dashboards or queries need the compatibility view. It stays, but only so an already-configured client can write before the code change lands (R4), and it can be dropped later.
3. **Backup and retention**: nightly `pg_dump`, 14 dailies on aegis-prod, plus rebuild-from-JSONL (R13). No offsite copy needed because the JSONL on each machine is the origin.
4. **powerstation (Windows)**: reader only. Ringer supports macOS and Linux (Windows via WSL), so powerstation reports through Grafana or DuckDB (`postgres` extension) with the reader role. If Ringer is ever run there, it runs in WSL with Python 3.12 and `psycopg`; nothing else on Windows is required.
5. **Port and exposure**: `100.100.1.21:5440`, bound to the Tailscale address only, direct (not behind the 443 proxy), `scram-sha-256` auth, and no public listener. Host port 5432 is avoided to prevent confusion with the unpublished Postgres containers of other apps.

## Verification plan (high level)
`python3 -m unittest discover -s tests` with `RINGER_NO_SELF_UPDATE=1`; schema applied to a throwaway Postgres twice (idempotence); legacy insert and new insert; dry-run `evidence push` against the 124-row local file reporting 124 rows would send, 0 duplicates; then (separately approved) apply to aegis-prod and repeat the push to confirm 0 new rows.
